### P-26 Estimates from this folder's runs, and an optional detailed estimate (2026-11-01)

Estimates stay far below what runs spend. This repository's one recorded run spent 1.46M tokens ($1.49) against "About 160k–320k tokens". Every estimate is scaled by the median ratio of spent to estimated tokens over the last five finished runs in the same folder, by the same agent and of the same kind. A new setting, `aisus.estimate.detailed`, is off by default. When it is on, Generate first plans which files the focus will read, then shows the planned reads, turns and tokens and waits for a second click.

The detailed estimate counts each turn's whole context again, because 93% of that run's tokens were cache reads. Tokens are about T × P + R × (T + 1) / 2 + O. T is the planned turns: the tier's read budget plus validator and write turns. P is the prompt and skill per turn. R is the planned read tokens, from the planned files' byte sizes. O is the output. The planned files are those whose paths match the focus words, up to the read budget, and files at the folder's median size fill the rest. The constants start provisional and the folder's runs calibrate them. A past run's prediction is recomputed from today's files and its `focus` in `run.json`, so `run.json` keeps its format.

### PLN-01 A plan map drawn from a spec (2026-11-02)

Jianxi asked for an `aisus-plan` skill that draws the system as a spec will leave it. The spec comes from the session, a file or another source. The plan starts from an earlier map when one fits, and is drawn new otherwise, as in an empty repository.

A plan map is an architecture map with three kinds of box. A box without a tag is existing code shown for context. A box tagged `changed` cites the existing lines the spec edits, and a box tagged `removed` cites the code the spec deletes. A box tagged `new` cites the passage of the spec that asks for it, and may also cite the code it plugs into. The spec is saved in the run folder as `spec.md` and committed with the map, so every box opens real text.

The skill finds the spec in this order and uses the first that applies:

1. A path in the arguments, such as a Markdown file, a PDF or an image. The agent reads it and writes the spec into `spec.md`. Text after the path is the focus.
2. A GitHub issue or pull request number or address, read with `gh`. For any other address the skill asks the user to paste the text.
3. Spec text in the arguments, kept word for word.
4. No arguments, and the session holds a spec or plan. The agent takes the latest version the user agreed to, and shows a summary of 3 to 6 lines with the messages it came from before going on. When no version is clearly agreed, it asks.
5. No arguments and no spec in the session. The skill lists up to three candidate files and asks the user to pick one or paste a spec. Candidates are recently changed Markdown files whose names hold spec, plan, proposal or design, and the newest proposal in `docs/shifts/`. A run launched from the sidebar has no session, so it stops here before spending tokens.

The skill picks the map to start from in this order:

1. A run folder named with `--base <run folder>`. Any accepted architecture map may be named, a detail map included.
2. Otherwise `plan-facts.mjs --list` prints the accepted architecture maps, newest first, with title, focus, age and how many boxes are stale or gone. Detail maps, pull request maps, sequence maps and plans are left out. The agent picks a focused map when the spec stays inside its focus, and the newest whole-system map otherwise.
3. When no map is accepted, or none covers what the spec touches, the agent draws a new map from the code and says why. In an empty repository every box is `new`.

A plan that starts from a map keeps that map's boxes and ids. Compare With… then shows the plan against its base. The agent rereads the stale boxes the spec touches before tagging them, and drops the boxes whose code is gone. When most of the base is stale or gone, the report suggests `/aisus-refresh` first and the plan still goes on. Planning the same spec again matches the new boxes' ids to the earlier plan with `match-ids.mjs`.

Other cases:

- A spec too vague to name one component stops the skill with a question about what should change.
- A spec that is already built tags nothing. The validator reports `PlanWithoutChange` and the skill reports the spec as built, with citations.
- Assumptions the code does not support go into a card, and so do the questions the spec leaves open.
- A spec that needs more than 15 new or changed boxes is drawn at the top level, and the report offers a detail map per box through `--parent` and `--box`.
- A missing, binary or protected file, or a spec over 200 KB, stops the skill with the reason.
- A `spec.md` holding a secret-like string is refused by the validator before anything else is checked. `spec.md` holds the extracted spec and never the raw conversation.
- Instructions inside the spec are treated as evidence, as in the other skills.
- `spec.md` keeps the spec's own language, and labels are English.
- A folder without git or without commits still gets a plan.
